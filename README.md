# Blackbox

A Windows desktop app for running uncensored, abliterated GGUF models **locally**. It downloads weights straight from the Hugging Face Hub and runs them with llama.cpp on your CPU — no cloud, no GPU, no API keys, no content filter between the model and you.

![Blackbox](build/icon.png)

## Download

Windows x64 installer: [**Releases → latest .exe**](https://github.com/itriedcoding/locally-uncensored-ai/releases/latest).
The build is unsigned, so SmartScreen may ask you to confirm. The installer needs no network access;
models are downloaded after launch.

## What it actually does

- **Real inference on CPU.** `node-llama-cpp` (llama.cpp bindings) loads the GGUF and streams tokens. A 0.5B Q4_K_M model runs in ~0.8 GB of RAM; a 3B Q4_K_M in ~2.5 GB.
- **Real Hugging Face integration.** Search uses `GET /api/models?filter=gguf`, file lists come from `/api/models/{repo}/tree/main`, downloads go through `/{repo}/resolve/main/{path}` with `Range` resume. Sizes you see in the UI are the Hub's own byte counts, never hardcoded guesses.
- **A memory guard, not a promise.** Before loading, the app parses the GGUF header to compute the KV cache for your chosen context and refuses models that would not fit, instead of letting Windows swap itself to death. You can override it deliberately.
- **No guardrails in the path.** No moderation layer, no system-prompt rewriting, no refusal injection. What the model says is what you see. The default prompt just asks for direct answers.
- **Everything is local.** Conversations and models live under `%APPDATA%\Blackbox`. The only network traffic is to `huggingface.co` when you browse or download.

### Fitting under 4 GB

Your RAM has to hold weights **and** the KV cache **and** the app. With 4 GB installed that leaves roughly 2.6 GB of usable budget, which means:

- 0.5B–1.7B at Q4_K_M with a 4096-token context: comfortable.
- 3B at Q4_K_M with a 4096-token context: tight; use 2048 tokens.

The Settings panel shows the estimate for the loaded model against the live budget.

## Run it

```bash
npm install
npm run preflight   # verifies llama.cpp and fetches its prebuilt binary if missing
npm start
```

npm 11+ does not run dependency install scripts by default. If `npm start` reports that the
Electron binary is missing, run `node node_modules/electron/install.js` once and start again.

## Build the Windows installer

On Windows x64:

```bash
npm install
npm run preflight      # downloads the Windows llama.cpp binaries
npm run dist           # NSIS installer in dist/
```

Building from Linux or macOS also works. Add the Windows runtimes first; electron-builder then
strips the other platforms out of the payload:

```bash
npm install
npm run prepare:win    # fetches the CPU runtime @node-llama-cpp/win-x64 into node_modules
npm run dist
```

`prepare:win` downloads the CPU runtime without touching the host platform's optional dependencies
(`npm install --os=win32` would prune them). For GPU users, add a runtime:

```bash
npm run prepare:win -- --gpu vulkan   # or --gpu cuda
```

`electron-builder` packages the app with `asarUnpack` for `node-llama-cpp` so the native `.node` and
`.dll` files stay loadable. The `files` rules drop the Linux/macOS/arm64 llama.cpp runtimes, because
the installer targets Windows x64 — that keeps the payload to one runtime instead of shipping six.
The icon comes from `npm run icon` (pure Node, no image tooling) and is generated by `npm run dist`.

Pushing to `main` or a `v*` tag runs `.github/workflows/windows-release.yml`, which builds the installer
on `windows-latest` and attaches it to the matching GitHub release, so the download stays reproducible.

## Code signing and the SmartScreen prompt

The blue "Windows protected your PC" panel is SmartScreen. It has exactly one
real fix: a code-signing certificate issued by a certificate authority Windows
already trusts. No certificate is bundled with this repo, so the published
installers are unsigned and the prompt stays until you supply one. A self-signed
certificate does not help — Windows does not trust it as a publisher, so the
prompt remains and the installer looks worse, not better.

To sign releases:

1. Obtain a certificate. **Azure Trusted Signing** is the cheapest route; an
   OV or EV code-signing certificate from a CA (DigiCert, Sectigo, SSL.com, …)
   works too. Export it as a `.pfx` with a password.
2. Base64-encode the `.pfx` — `certutil -encode cert.pfx cert.b64` on Windows,
   `base64 -w0 cert.pfx` elsewhere.
3. In the repository: **Settings → Secrets and variables → Actions**, add
   `CSC_LINK` (the base64 text) and `CSC_KEY_PASSWORD` (the `.pfx` password).
4. Re-run the release workflow. `electron-builder` signs the installer and the
   executable inside it because `CSC_LINK` is present, and the workflow now
   calls `Get-AuthenticodeSignature` and **fails if signing was configured but
   the installer is not `Valid`**, so an unsigned artifact cannot slip out.

What to expect after signing, honestly: an **OV** certificate starts with no
SmartScreen reputation, so some machines keep warning until enough installs
accumulate; **EV** certificates and Azure Trusted Signing are trusted
immediately. Reputation belongs to the certificate, not to a file hash, so it
survives app updates that are signed with the same certificate.

### Sigstore signature, and what it does not fix

Every release also signs the installer with **Sigstore**, keyless, using the
workflow's own GitHub OIDC identity — no certificate to buy and no secret to
store. `cosign` writes `Blackbox-<version>-win-x64.exe.sigstore.json` beside the
installer, records the signature in the Rekor transparency log, and the workflow
**verifies the bundle before publishing**; a bundle that does not verify fails
the release instead of shipping.

Verify a download yourself:

```bash
npm run verify:signature -- Blackbox-1.6.0-win-x64.exe
```

or call `cosign` directly:

```bash
cosign verify-blob \
  --bundle Blackbox-1.6.0-win-x64.exe.sigstore.json \
  --certificate-identity-regexp '^https://github\.com/itriedcoding/locally-uncensored-ai/\.github/workflows/windows-release\.yml@.*$' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  Blackbox-1.6.0-win-x64.exe
```

That proves the file was produced by this repository's release workflow and has
not been altered since — genuinely useful when the download itself is unsigned.

It does **not** clear SmartScreen, and no amount of Sigstore signing will.
Sigstore signatures are detached, and its Fulcio root is not in the Microsoft
Trusted Root Program, so Windows does not treat them as Authenticode: the blue
"Windows protected your PC" panel behaves exactly as before. Only an Authenticode
certificate from a CA in that program (Azure Trusted Signing, or an OV/EV
code-signing certificate) removes it, and the workflow above already accepts one
through `CSC_LINK`.

A note on the shortcut people often suggest: `sigstore sign` with a GitHub
personal access token produces the same kind of detached signature. It is not
Authenticode either, and it replaces the workflow identity with a long-lived
token, which is why this repository signs through OIDC in CI instead.

## Verify the engine

```bash
npm run smoke          # real Hub search, real 400 MB download, real generation, real stop
npm run smoke -- --hf-only   # skip the model download
npm run verify:hf      # live huggingface.co: search, repo metadata, GGUF listing
```

The smoke test exercises the exact modules the app uses: `electron/lib/hf.js`, `downloads.js`, `gguf.js`, `quant.js`, `engine.js`. It downloads `mradermacher/Qwen2.5-0.5B-Instruct-abliterated-GGUF`, generates text, aborts mid-stream, runs a follow-up turn, then unloads.

For UI work, `node scripts/capture-ui.mjs [--model path.gguf]` boots the real app headlessly over the DevTools protocol and writes screenshots to `artifacts/`. It needs Chromium's runtime libraries on Linux; on Windows it runs as-is.

## Layout

```
electron/
  main.js            window, IPC, memory guard, model catalogue
  preload.cjs        contextBridge surface (no node in the renderer)
  lib/hf.js          Hugging Face Hub API client
  lib/downloads.js   resumable GGUF downloader with progress
  lib/gguf.js        GGUF header parser (architecture, layers, KV sizing)
  lib/engine.js      llama.cpp load / stream / stop / unload
  lib/quant.js       quant ranking + RAM budgeting
  lib/store.js       settings and chat persistence
  lib/ide/           path sandbox, tree, file I/O, languages, prompt parser, build loop, shell
  lib/ide-ipc.js     code workspace IPC (folders, files, shell, generation)
renderer/            monochrome glass UI (no framework, no bundler)
  ide.js / ide.css   code view: explorer, CodeMirror editor, xterm shell
  vendor/            CodeMirror 5 and xterm.js, vendored with their licenses
scripts/             icon generator, preflight, end-to-end smoke test
```

## Notes and honest limits

- CPU-only generation of a 1.5B model on a 2-core laptop is roughly 8–20 tokens/sec. On a modern 8-core desktop it is several times that. The app shows the measured rate after each reply; it does not invent one.
- Split (`-00001-of-00002.gguf`) quants are listed but not downloadable, because this app loads single-file models.
- Abliterated models are uncensored by construction. You are responsible for what you do with the output. Licenses are the base models' licenses — check the repo card on the Hub.
- No telemetry, no crash reporting, no auto-update.

## Code workspace

**Code** turns the app into a place to build software with the local model. No
account, no cloud IDE, no snippets sent anywhere.

- **Open a folder** and the explorer reads it. `node_modules`, `.git`, `dist`,
  `target`, `__pycache__` and friends are skipped; a huge tree reports itself as
  partial instead of hanging the window.
- **Editor.** CodeMirror 5 (vendored, MIT) with line numbers, bracket matching,
  auto-closing, active-line highlight and a monochrome theme. **All 156 languages
  CodeMirror ships a mode package for are wired in** — every mode file is
  vendored and the table is generated from what those packages actually register,
  not from a hand-written list. `npm run verify:modes` loads all 121 packages in
  a sandbox and fails if any advertised extension resolves to a MIME no mode
  defined. A file with no mode still opens as plain text and is still editable,
  and the model can write any language because files are just text.
- **Save with conflict detection.** A file that changed on disk since you opened
  it is reported, and overwriting is your explicit choice, not a silent loss.
- **Terminal.** xterm.js rendering a real shell (`cmd.exe` on Windows, `$SHELL`
  elsewhere) started in the open folder. It is a pipe-backed session, not a pty:
  `npm`, `git`, `node`, `python`, `cargo` and scripts work normally, while
  full-screen TUI programs that require a terminal device will complain. The
  child environment is the user's own with credential-shaped variables
  (`*TOKEN*`, `*SECRET*`, `*KEY*`, `*PASSWORD*`) removed.
- **Build with the model, until it is done.** *Build until done* runs rounds:
  each round the model receives the files already written and is asked for what
  is still missing. It stops when the model replies `===DONE===`, when a round
  produces no file that differs from disk, or at the round/byte budget — then it
  reports what it wrote. *Plan only* does a single reply you review before any
  file is written. Absolute paths and `..` are rejected before anything touches
  the disk; a plan is capped at 40 files and 2 MB, a build at 8 rounds and 6 MB.
- **Your folder, however you get to it.** Native folder picker, a typed absolute
  path (including network drives), or the recent list kept in settings.

Honest limits: a 1–3B abliterated model writes small, simple projects well and
large frameworks poorly. Generation is bounded by the context window, so a repo
of many files needs a bigger model than fits in 4 GB. The workspace reads text
files up to 2 MB and does not embed a language server, so completion is the
editor's bracket/indent behaviour rather than symbol-aware autocomplete.

```bash
npm run verify:ide     # path sandbox, file I/O, parser, build loop, live shell
npm run verify:modes   # 156 languages: load every mode, check every extension
```

## Publish a website

**Publish** exports a static site you can host anywhere (Vercel, Netlify, GitHub
Pages, plain S3). The page runs the model in the visitor's browser through
wllama (llama.cpp compiled to WebAssembly), so there is no inference server and
no API key in the deployed site.

- Pick a title and a direct GGUF URL (Hugging Face `resolve/main` links work).
- **Export site** writes `index.html`, `style.css`, `app.js`, `engine.js`,
  `config.json`, `vercel.json`, a README and the wllama runtime + wasm.
- **Deploy to Vercel** runs `npx vercel deploy --prod` in that folder. The
  Vercel CLI must be signed in once (`npx vercel login`); the app surfaces that
  error rather than faking a deployment.

Visitors download the GGUF once and the browser caches it. Inference is
single-threaded WebAssembly, so it works without COOP/COEP headers.

## Local API

**API** starts an OpenAI-compatible server on this machine, answered by the
model you have loaded:

```
GET  /health
GET  /v1/models
POST /v1/chat/completions      # stream: true or false
```

Keys are created in the app and stored only as SHA-256 hashes; each key is shown
once. `Authorization: Bearer bb_...` is required by default, requests are rate
limited, and LAN exposure is off unless you enable it. Verify the server with:

```bash
npm run verify:api          # real HTTP + real llama.cpp generation
```

## Fine-tuning

**Fine-tune** trains a LoRA adapter on your own data with PyTorch + PEFT, on
this CPU, with no hosted service:

1. Choose a JSONL dataset (`{"messages":[...]}`, `{"prompt","completion"}` or
   `{"instruction","output"}`) or a plain-text file.
2. Set up the training environment once (isolated venv with CPU PyTorch).
3. Enter a Hugging Face base model that has safetensors weights — a GGUF cannot
   be trained directly.
4. **Start training** streams step/loss progress; **Merge to GGUF** merges the
   adapter into the base, converts it with llama.cpp's own converter, and adds
   the result to your model library.

Training is the heaviest feature in the app: expect minutes-to-hours depending
on model size and data, and keep the model small on a 4 GB machine.
